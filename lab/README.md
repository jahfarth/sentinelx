# SentinelX Attack Lab

A self-contained, intentionally vulnerable playground for testing the
SentinelX detection engine end to end. It ships a weak Flask app + SSH box
(`lab/target`) and a set of attack scripts (`lab/attacks`) that reproduce
common attacker behavior. The API/worker ingest the resulting logs and the
detection engine fires the alerts listed in the mapping table below.

## ⚠️ Safety disclaimer

- **Lab use only.** The target is deliberately vulnerable (SQL injection,
  reflected XSS, weak credentials). Never expose it to the internet or a
  network you don't fully control.
- All attack scripts target `$TARGET`, which defaults to `127.0.0.1`.
  Only ever point them at your own lab container.
- The target runs in an isolated Docker Compose profile (`lab`) — it does
  not start with the normal stack.

## Quickstart

1. Start the core stack, then the lab target:

   ```bash
   docker compose up -d
   docker compose --profile lab up -d target
   ```

2. From the host, run the full lab scenario (attacks the ports published
   on localhost; `2222` → SSH, `5000` → Flask):

   ```bash
   cd lab/attacks
   ./run_all.sh
   ```

   Or target the container by its compose hostname from inside the lab
   network:

   ```bash
   TARGET=target ./run_all.sh
   ```

3. Open the dashboard at http://localhost and check the alerts list, or
   query the API: `curl http://localhost:8000/alerts`.

## Expected detection mapping

| Attack (script)            | Firing rule(s)     | MITRE technique | Severity |
|----------------------------|--------------------|-----------------|----------|
| Port/service recon (01)    | SX-PORT-SCAN       | T1046           | medium   |
| SSH password guessing (02) | SX-BRUTE-FORCE     | T1110.001       | high     |
| HTTP login guessing (02)   | SX-BRUTE-FORCE     | T1110.001       | high     |
| SQL injection probe (03)   | SX-WEB-ATTACK      | T1190           | high     |
| Reflected XSS probe (04)   | SX-WEB-ATTACK      | T1190           | high     |

Notes:

- The exact alert depends on the log pipeline actually feeding the
  detector (see `docs/10-lab-guide.md`); the mapping above is what the
  rules are designed to fire on.
- The ML anomaly detector (`ml-anomaly`) may additionally fire on the
  attack bursts, since the traffic volume deviates from the benign
  baseline generated by `05_baseline.py`. That's expected — run the
  baseline first so the model has "normal" to compare against.
- Sigma rules such as `web_sqli_probe.yml`, `web_xss_probe.yml`,
  `auth_failed_password.yml`, and `ssh_failed_root_login.yml` cover the
  same signals for pipelines that run the Sigma set.
